# Интеграция и интерфейс для MVP

Роль 4 связывает готовые модули команды, показывает результат и обеспечивает запуск.
Рабочая ветка основана на `feature/budget` (работа роли 3, PR #1). Перед объединением
этой части в main нужно принять PR #1 и провести ревью интеграции.
Схемы `schemas/models.py`, поиск, планировщик, калькулятор и критик не изменены.

## Что реализовано

- `run_workflow(request) -> PlanningResult` сохраняет прежний контракт.
- `run_workflow_with_trace(request) -> WorkflowRun` добавляет отдельную обёртку
  для UI: сохранённый request, result, agent_trace, error и mode.
- Пайплайн: поиск → планировщик → валидатор (внутри вызывает критика при ошибках)
  → передача всех issues планировщику → повторная проверка. Максимум два меню.
- В trace сохраняются обе оценки, рекомендации критика внутри issues, feedback,
  выбранные ID, время и статус каждого завершённого шага. Это журнал событий,
  а не внутренние рассуждения модели. `status=ok` у валидатора означает успешный
  вызов функции; пригодность меню определяется `assessment.valid`.
- UI показывает меню по дням с названиями, корзину, стоимость, нарушения, trace
  и выгрузку JSON. Результат сохраняется между перезапусками Streamlit. После
  изменения полей есть явное предупреждение, что показан старый запрос.
- Нет подходящих рецептов, ошибка чтения данных или сбой планировщика дают
  понятную ошибку. Текст исключений провайдера не показывается. После сбоя
  повторного прохода старое невалидное меню не выдаётся как окончательное.
- `.env` читается локально; уже экспортированные переменные имеют приоритет.
- Docker Compose, проверка health, запуск без root, шаблон CI с тестами и
  проверкой контейнера (`docs/github-tests.yml`). Для включения перенести его
  в `.github/workflows/tests.yml` с GitHub-доступом, разрешающим workflows. Секреты и локальное окружение исключены из build context.

## Сценарии и проверки

Все команды выполняются из корня репозитория после установки зависимостей.

```bash
python -m pytest -q
python scripts/run_demo.py fixtures/request_basic.json
python scripts/run_demo.py fixtures/request_over_budget.json
```

Второй запрос должен завершиться кодом 1 и JSON с `valid=false`, превышением
бюджета, советом `Critic [mock]` и двумя попытками. Mock-планировщик пока не
меняет выбор по feedback; успешный пересмотр проверяется интеграционным тестом,
который подставляет только ответ планировщика, а расчёты и проверку использует
настоящие. Это не доказательство работы живой LLM.

`request_no_match.json` используется вместе с `recipes_empty.json`, а
`request_missing_price.json` — с `prices_missing.json`. Тесты подменяют пути к
каталогам через monkeypatch, не перезаписывая общие данные. CLI использует
обычные данные `examples/`; один request без тестового каталога эти ошибки
не создаёт. `mock_candidates`, `mock_plan`, `mock_assessment` соответствуют
действующим схемам репозитория, а не примерной схеме из Word.

```bash
cp .env.example .env
docker compose up --build
# В другом терминале:
curl --fail http://localhost:8501/_stcore/health
docker compose down
```

## Настройка Gemini

Это подготовленная конфигурация, а не утверждённый выбор команды и не отчёт о
живом тестировании. Google предоставляет OpenAI-compatible endpoint, поэтому
переписывать агенты для подключения Gemini не требуется:
https://ai.google.dev/gemini-api/docs/openai

Получить ключ можно в https://aistudio.google.com/apikey. В локальном `.env`:

```dotenv
MOCK_LLM=false
LLM_API_KEY=YOUR_LOCAL_GEMINI_KEY
LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
LLM_MODEL=gemini-3.1-flash-lite
CRITIC_MODEL=gemini-3.1-flash-lite
```

На 20 октября 2026 в документации эта модель имеет free tier; доступность и
квоты зависят от проекта Google и могут меняться:
https://ai.google.dev/gemini-api/docs/pricing#gemini-3.1-flash-lite
Проверьте доступность модели в своём AI Studio. Ключ хранить только локально,
не в сообщениях, JSON-выгрузках, коммитах или скриншотах. После изменения `.env`
полностью перезапустить приложение или контейнер.

Живая проверка: сначала обычный запрос, затем пустой pantry и бюджет 0.
Во втором случае в trace должны быть ответы `Critic [LLM, issue ...]`,
feedback во второй попытке и повторная Python-оценка. Невыполнимый бюджет может
остаться невалидным — это корректный результат. Для демонстрации успешного
пересмотра нужен запрос, при котором первое меню превышает бюджет, но более
дешёвое меню доступно; выбор первого меню LLM заранее не гарантирован.
Сохранить JSON через кнопку UI и отдельно записать фактические модель/провайдера
и результат проверки. `Critic unavailable` не считается успешным вызовом критика.

## Что необходимо получить от команды

1. Роль 1: настоящий подготовленный набор рецептов и согласованный прайс-лист.
   В текущем каркасе только три демонстрационных рецепта.
2. Роль 2: проверенный настоящий LLM-планировщик, обработка некорректного JSON
   и сетевых сбоев с ограниченными попытками. Сейчас оркестратор безопасно
   показывает сбой, но не переписывает реализацию владельца модуля.
3. Роли 2–3: согласованные провайдер/модель и реальный прогон полного цикла.
4. Все участники: ФИО и GitHub-ники для README.

Текущий контракт использует `pantry: list[str]`, EUR, условные `portion`,
одного человека. Количества запасов и масштабирование servings не реализованы
калькулятором; UI не обещает их поддержку. Улучшение требует согласования
контракта и владельцев данных/калькулятора. LangGraph не добавлен: линейного
Python workflow с одним условным пересмотром достаточно для текущего MVP.

## Сценарий рассказа на защите

Показать запрос и меню, затем бюджет 0 и trace с обратной связью и повтором.
Объяснить: поиск даёт кандидатов, LLM выбирает меню, Python проверяет факты,
отдельный LLM-критик советует изменения, Python проверяет новое меню.
Роль 4 хранит состояние и историю, ограничивает цикл и показывает честный итог.
