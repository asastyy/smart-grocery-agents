# Роль 3 — интеграция результатов участников 1 и 2

Ветка `feature/budget-foodcom` включает исходную роль 3 (PR #1),
данные и поиск роли 1 из PR #3 (`78cca979`) и планировщик роли 2
из PR #4 (`233b0bd4`). Это локальное объединение веток для проверки;
PR участников не объединялись в main. UI роли 4 из PR #2 не включён.

## Что готово

- Чтение 150 рецептов из `data/recipes.jsonl` и 503 демо-цен из `data/prices.csv`.
- Пересчёт ингредиентов: `quantity * meal.servings / recipe.servings`.
- Суммирование продуктов по всем блюдам и дням, затем однократное вычитание
  суммарных домашних запасов. Отрицательные остатки не попадают в покупки.
- Проверка обеда и ужина на каждый день, порций, ID кандидатов, тегов диеты,
  времени приготовления, единиц, валюты и бюджета.
- Отсутствующая цена сохраняет позицию корзины с `cost: null`.
- LLM-критик адаптирован к новому результату; исходные нарушения и расчёты
  остаются неизменными, рекомендации попадают в `feedback`.
- Новый workflow вызывает реальные функции ролей 1 и 2, явно передаёт
  `slots=("lunch", "dinner")`, ограничивает общих кандидатов первыми 20
  (лимит планировщика) и допускает только одну перепланировку.
- `agent_trace` сохраняет обе попытки, включая рекомендации критика.

## Контракты для интегратора

Детерминированный инструмент:

```python
from smart_grocery.tools.budget import evaluate_plan
assessment = evaluate_plan(request, plan, catalog)
```

Валидатор с критиком:

```python
from smart_grocery.agents.validator import validate_foodcom_plan
assessment = validate_foodcom_plan(request, plan, catalog)
```

`catalog = {"recipes": candidates, "prices": load_prices()}`. В recipes должны
быть именно кандидаты, доступные планировщику, не произвольные рецепты.
Запрос: `fixtures/request_foodcom.json`. Pantry — список объектов с
`ingredient_id`, `quantity` и `unit`; диета — список тегов, валюта — CU.
План — результат `plan_meals`: meals с day, slot, recipe_id, servings.

Результат содержит `valid`, `total_cost`, `shopping_list`, `violations`,
`feedback` и дополнительное поле `priced_subtotal`. При неполных данных
`total_cost=null`, `priced_subtotal` — сумма только корректно оценённых строк.
В строке корзины `unit_price` и `cost` могут быть null. Это явное уточнение
нового словарного контракта для роли 4: не подставлять нули и не форматировать
null как число. Старые общие модели Pydantic не изменены.

Полный запуск:

```python
from smart_grocery.workflow.foodcom import run_foodcom_workflow
result = run_foodcom_workflow(request)
# result = {plan, assessment, agent_trace}
```

Старый runner и app.py используют отдельный `legacy_recipes.py`, чтобы
оставаться воспроизводимым примером старого контракта. Это не путь к Food.com.
Два конфликтовавших mock_candidates сохранены раздельно:
`mock_candidates.json` — роль 1, `planner_candidates.json` — короткая фикстура роли 2.

## Локальный запуск Windows

Из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:MOCK_LLM = 'true'
.\.venv\Scripts\python.exe -B scripts/run_foodcom.py
.\.venv\Scripts\python.exe -m streamlit run app_foodcom.py
```

Для браузера: бюджет 25, 3 дня, 2 человека, 30 минут, запасы `[]`.
Ожидается 6 блюд. С бюджетом 0 ожидается невалидный результат и 2 попытки.
Mock-планировщик не использует замечания для улучшения меню; это демонстрация
передачи feedback, не успешной оптимизации с LLM.

Planner теперь автоматически читает `.env` (из PR #4); переменные текущего
процесса имеют приоритет. Для живой проверки нужны `MOCK_LLM=false`,
выбранные бесплатные модель/провайдер и ключ. Значения модели из документации
участника 2 не являются гарантией бесплатного доступа. Локально подтверждён настоящий ответ Gemini-критика; пользователь также
подтвердил ручную проверку приложения. Настройка описана в `docs/CRITIC.md`.

## Проверка и ограничения

76 тестов прошли, включая исходные тесты ролей 1–3, SDK-критика с подставным
HTTP, количественный pantry, масштабирование порций, неполные цены,
передачу feedback, новый workflow на данных Food.com и AppTest обоих экранов.
`scripts/check_data.py`: 150 рецептов, 503 ингредиента, 503 цены.
Пользователь подтвердил ручную проверку экрана в браузере. Docker не проверялся
и пока запускает старый `app.py`, а не `app_foodcom.py`.

Найдена проблема данных: в каталоге rice, water, milk и другие ингредиенты
могут иметь единицу pcs. Например, tomato_juice в r001 имеет 46 pcs.
Мы сохраняем исходные данные и не придумываем пересчёт. Для базового запроса
текущий mock-план даёт всего 0.06 CU — это демонстрационный результат по
предоставленному прайсу, а не экономически правдоподобная стоимость еды.
Автору данных нужно проверить извлечение единиц и нормализацию количеств.
Обнаруженное несовпадение единиц между рецептом, запасами и ценой блокирует
валидность, но одинаково ошибочные единицы во всех файлах автоматически
распознать нельзя. Проверка диеты по-прежнему доверяет тегам роли 1.

Перед объединением: роль 4 подключает новый workflow или соответствующий
валидатор к своему trace/UI; роль 1 проверяет семантику единиц; команда
проверяет итоговую общую сборку. Локальный живой вызов уже подтверждён.

## Интерфейс и примеры для ревью

Запасы добавляются через выбор продукта и количества, без ручного JSON.
Есть поиск рецептов и статус критика для каждой попытки. Критик вызывается
при нарушениях; максимум две попытки меню. Его последний ответ сохраняется,
но не запускает третью попытку.

В mock-режиме: `python scripts/run_foodcom.py fixtures/request_foodcom.json`
даёт валидное меню; `fixtures/request_over_budget.json` — `over_budget`
и две попытки; `fixtures/request_no_match.json` — `no_candidates`.
Файл `fixtures/evaluation_missing_price.json` содержит request, plan и catalog
для вызова `evaluate_plan(**fixture)`: ожидаются `missing_price`, `valid=false`,
`total_cost=null` и сохранённая строка корзины с `cost=null`.
